# Agent 通信协议初步方案

状态：设计提案。自然语言/ACP-1双路径已接入，当前范围和限制见[实现说明](COMMUNICATION_IMPLEMENTATION.md)；通用状态增量和并发DAG不代表全部已实现。独立数字协议示例已由正式实现替代并清理。真实API批次及未完成状态见[结果索引](../reports/README.md)，旧实验不改写。

## 目标与边界

实现“数字操作码 + 类型化参数 + 统一返回 + 能力协商 + 引用式状态”的应用层协议。可运行于进程内消息队列、Pipe 或 Unix Socket；协议语义不绑定具体传输方式。角色适配器将模型意图转为协议消息，确定性解析器校验后由运行时派发。模型仍读取必要的题干、查询含义和证据，不能假定任意数字具有预训练语义。

收益分开验证：二进制编码减少实际消息字节与重复序列化；对象引用减少重复搬运；按角色构造必要上下文及精简生成字段才可能减少模型 Token。现有控制信息本来就不进入模型，不能重复计算 Token 收益。

## 参与方与消息结构

| ID | 参与方 | 是否 LLM Agent |
| --- | --- | --- |
| 0 | 运行时/调度器 | 否 |
| 1 | Planner | 是 |
| 2 | Investigator | 是 |
| 3 | VerifierReasoner | 是 |
| 4 | Textbooks 工具服务 | 否 |
| 5 | 共享记忆服务 | 否 |

固定头部沿用独立解析示例的布局，网络字节序共 18 字节：

`version:u8 | kind:u8 | src:u8 | dst:u8 | opcode:u16 | task_id:u32 | request_id:u32 | body_length:u32`

`kind=1` 请求，`2` 结果，`3` 错误。字段位置和类型确定含义；消息体由对应 opcode 的 schema 解码，不用无分隔数字串猜测边界。固定参数使用固定布局，变长字符串/数组采用长度前缀。文本按 UTF-8 编码，数值明确类型；参数是对象引用时还需校验任务、对象类型和版本。

统一结果复用原 task_id、request_id、opcode，交换 src/dst，消息体按该操作的返回 schema 编码。错误包含错误码、可选诊断引用及可重试属性。初步错误码覆盖未知版本/动作、参数无效、引用不存在、权限不足、预算耗尽、工具失败和请求结果未知。

## 动作、参数和返回结果

表中参数名称是文档说明；二进制线上按照 schema 编码。工具候选数量、阈值、预算等由运行时配置或在允许范围内校验，不给模型任意修改配置的权限。

| 操作码 | 能力 | 输入参数 | 返回结果 |
| --- | --- | --- | --- |
| 1 | HELLO：建立会话 | 支持的协议版本、Agent ID、能力描述版本 | 接受版本、会话状态、能力版本 |
| 2 | CAPABILITIES：注册或查询能力 | Agent ID、操作码、输入/输出类型、版本、必要约束 | 已注册的能力表或拒绝原因 |
| 10 | TEXTBOOK_SEARCH | query_ref、top_k；索引与重排配置由运行时提供 | source_refs、候选排名、来源版本；模型视图不必包含排名 |
| 11 | SOURCE_READ | source_ref、允许的区间或展开方式 | evidence_ref、原文区间及内容版本 |
| 20 | MEMORY_READ | memory_refs、任务作用域 | 已解析记忆引用、类型和必要内容引用 |
| 21 | MEMORY_RECALL | float32 向量或向量引用、模型/维度、阈值、limit、类型集合 | 候选记忆头部、分数、版本；先投递短预览 |
| 22 | MEMORY_PUT | 记忆单元引用、float32 向量、来源关联 | memory_id、写入或去重状态 |
| 30 | EVIDENCE_DELIVER | source_ref、原文区间、关联需求 ID | 已登记的 evidence_ref、可见区间版本 |
| 31 | STATE_DELTA | state_ref、base_version、新版本、增改删项 | 已应用版本或需要快照的错误 |
| 40 | ANSWER | 选项码、必要短解释、证据/片段引用列表、声明支持状态、关键缺口 | 已接收答案、引用核验结果、独立协议状态 |
| 41 | FOLLOWUP | 关键缺口、可能影响答案的原因、需求/证据引用、查询引用 | 接受/跳过原因、新证据引用；保留原答案 |
| 50 | PLAN | task_ref、候选记忆预览、必要约束 | plan_ref；包含条件、需求及选中的记忆引用 |
| 51 | QUERY_PLAN | task_ref、plan_ref、可用记忆/证据引用、执行约束 | query_plan_ref；查询文本、需求关联、条件及依赖 |
| 60 | BATCH：多操作批次 | 批次策略、带独立 op_id 的子操作列表及依赖 | 按 op_id 返回状态、结果引用或错误；可逐项回传 |

示例：`src=2,dst=4,opcode=10,task_id=17,request_id=42`，消息体 `query_ref=1001,top_k=3`。服务查找任务 17 的查询对象 1001，验证其类型和来源后执行检索。数字本身不能还原一个尚未存储的查询。

角色能力白名单应与当前实际路径一致：Planner 负责规划与记忆选择；Investigator 负责查询计划；VerifierReasoner 负责答案与可选补查。模型不直接访问任意工具，服务请求由运行时将已校验的计划展开。当前 decoupled 路径不能把 strict 路径的所有可选动作都宣称为已开放能力。

## 握手、能力发现与派发

1. 启动后各角色适配器及工具服务发送 HELLO；运行时选择双方支持的协议版本，返回同 request_id 的结果。
2. 注册能力，至少包含 opcode、输入 schema、返回 schema 和约束。能力表由运行时缓存，后续消息不携带全量说明。
3. 请求到达后依次校验消息长度和版本、发送方权限、目标能力、参数类型与范围、对象引用、当前预算。
4. 根据能力注册表派发到确定函数，返回同 request_id 的 RESULT 或 ERROR。未知操作不能通过自然语言兜底为任意工具调用。
5. 对已完成的重复请求，复用已持久化结果；请求仍在执行或远程响应未知时返回明确状态，不以“同一请求 ID”为由宣称远程 API exactly-once 或自动重发。

这使握手成为决定是否接受后续请求的实际逻辑，而非只导出一份名字为 handshake 的配置文件。注册表还应驱动文档和实际派发，避免能力声明与代码分支不一致。

## 多操作批次与多步执行

一个 Agent 的一次输出可以包含多个操作；一次消息不等于只能有一个业务步骤。外层使用 BATCH=60，目标为运行时，task_id 标识任务，request_id 标识批次；消息体包含操作数量和长度有界的子操作记录。初版限制每批至多 16 项，不能绕过原任务的模型、检索、回读或时间预算。

每个子操作包含：

`op_id:u16 | dst:u8 | opcode:u16 | depends_on:[op_id] | run_if:enum | failure_policy:enum | typed_args`

操作身份为 `(task_id, request_id, op_id)`；opcode 表示做什么，op_id 表示这是本批次的哪一次操作，两者不能混用。同一 opcode 可出现多次，结果不依赖返回顺序对齐。

`depends_on` 表达真实执行前置条件或产物依赖。无依赖且符合权限与预算的操作可以并行；有依赖的操作在指定条件满足后启动。初版仅允许引用同批次前面定义的 op_id，校验缺失依赖和重复 ID，因而不能形成环。是否并发、并发上限和资源预留由运行时决定，发送者不能以声明并行突破预算。

`run_if` 至少覆盖成功依赖满足、指定前驱为空/无新来源、指定前驱工具失败等条件；条件必须绑定明确前驱，不能把“未返回”当成“空结果”。多个前驱默认全部满足，部分结果即可继续时必须在 schema 中明确允许，并把失败和缺失来源告诉接收角色。

示例：Investigator 已登记查询 1001、1002 和备用查询 1003，发送一个批次：

| op_id | 接收者 | 操作 | 参数 | 依赖与条件 |
| --- | --- | --- | --- | --- |
| 1 | 教材工具 | SEARCH=10 | query_ref=1001，top_k=4 | 无依赖 |
| 2 | 教材工具 | SEARCH=10 | query_ref=1002，top_k=4 | 无依赖；可与 1 并行 |
| 3 | 教材工具 | SEARCH=10 | query_ref=1003，top_k=4 | 依赖 1；仅当 1 完成且没有新内容时执行 |

这是三条明确查询计划，不是三个 LLM Agent 调用。批次完成后运行时汇总有效证据，交 VerifierReasoner；若把下游角色调用放入批次，仍须登记其请求/结果 schema 与允许路由。现有 ANSWER=40 描述答案提交，不能直接假称已实现一个通用的“调用验证角色”接口。

参数可以用类型化结果引用表示前驱产物：`RESULT_REF(request_id, op_id, field_id)`。只有前驱返回且结果类型符合下游 schema，才能替换为实际值；不得把占位数字直接当工具参数执行。新文本仍需内联携带或先登记对象，不能引用尚不存在的任意内容。

每个子结果返回 `op_id、状态、result_ref 或 error_code`，状态至少为 queued、running、succeeded、failed、skipped、cancelled；空结果是 succeeded 加显式空集合，不等于失败或尚未返回。条件未触发时返回 skipped，批次状态可为完成、部分失败或失败。允许逐项返回并在末尾给汇总，避免等到最后只收到一个难以定位的错误。

执行失败时，初版默认阻断依赖失败项的子操作，独立分支按各自 failure_policy 处理。提交答案、写入记忆等有副作用的动作必须单独受保护，不提供整个批次原子回滚的假承诺。重复批次只重用已落盘的子结果；执行中、远程响应未知或有副作用的项目不能自动重新发送。每一实际调用单独登记检查点、预算和用量，重试不获得新额度。

现有 Investigator 查询计划已经有 `id、run_if、after` 的局部机制，适合迁移到这一通用批次格式；不能把“知识需求相关”自动转成必须串行等待的执行依赖。该通用 BATCH 仍是设计，不代表现有独立解析示例已支持。

## 引用、模型视图与状态同步

任务存储保存原题、全部选项；规划存储保存条件和需求；证据存储按语料版本及内容哈希保存原文与区间；共享记忆保存规定的 ID、来源 Agent、创建时间、主题和摘要等元数据。首次登记对象的成本必须计入实验。

引用绑定 task_id、对象类型和不可变内容版本。跨任务记忆使用持久化 ID 或内容哈希，不按局部数字碰巧相同复用。状态增量带基线版本，接收方基线缺失时请求快照；不能悄悄把增量应用到旧状态。

模型输入分别构造：

- Planner：当前原题/选项、最多少量候选记忆预览、规划所需约束。
- Investigator：原题中检索所需条件与选项、当前需求、采用的策略/证据、可执行约束。是否能安全减少原题需实验，不能直接认定规划已覆盖全部条件。
- VerifierReasoner：原题和全部选项、必要需求、已选择原文、真实冲突及关键缺口；不强制重复全部查询历史、执行控制和未用记忆。

模型只生成需要判断的内容。请求 ID、时间、路由、类型固定值由程序补齐；查询执行条件、支持状态等可采用紧凑枚举。引用可用预编号原文片段，程序还原引句并校验，避免模型重复抄写；不要求模型数长文本的字符下标。医学适用性、推断理由及真正的关键缺口不能由程序随意补造。

嵌入继续使用 float32 二进制交换，接收端实际用于记忆检索。数字操作码和对象 ID 主要属于结构化协议，不能单独替代非文本语义状态的验证。云模型的独立请求不会自动保留上一角色上下文；程序状态增量也不等于模型可以省掉所有必要背景。

## 实施与验证顺序

1. 将动作和参数/结果 schema 固定为一份注册表；实现双向解析、真实握手、能力白名单派发及错误响应。
2. 接入现有运行时，保持角色、题目、检索、证据正文和模型设置不变，验证行为与结果一致。JSON 调试输出可保留，实际 Agent 通道使用字节帧。
3. 接入对象注册、引用校验、状态版本和增量同步；按角色减少无用输入，缩短机械性输出；这一阶段另标版本并验证准确率。
4. 先用已有响应做无付费回放，记录总消息字节、登记与补取成本、解析耗时和往返一致性；再对真实模型做小样本检查，通过后执行固定三组 30 题的完整对照。

格式与内容压缩分别消融：现有 JSON 与数字二进制使用相同内容以测字节收益；完整模型视图与必要模型视图比较以测 Token 及质量。纯文本基线提供同等必要信息，不人为添加无用历史。正文与模型输出、字典成本、状态交换及 CPU 耗时全部统计，不把 26 字节演示包的缩小比例当作整题收益。

已有 360 条模型响应的离线实验中，只将预定义字段名/枚举改为数字，在不计模型理解码表的理想化情况下，全文 Token 计数仅减少约 3.6%–3.8%；如果每次附完整公共码表则反而增加。见 `experiments/validation/medical30-numeric-token-ablation-20261020/report.md`。这说明明显的 Token 降幅应来自必要上下文与生成内容的减少，不能预先承诺由二进制传输自动获得。该实验未验证模型在新编码下的答题质量。
