# G²CP 论文、仓库实现与实验分组对照核查

核查日期：2026-10-20。读取当前源码、已有实验及原论文；不改运行时代码，不覆盖历史结果，不产生新 API 请求。

本报告描述修正前的实验和实现。之后已按用户要求接入自然语言与 ACP-1 双路径，见 [实现说明](COMMUNICATION_IMPLEMENTATION.md)。以下源码位置与模式对比作为历史核查保留，不代表新实现仍走同字段格式分支。

## 结论

当前实验能比较同字段可读文本与紧凑 JSON 的差异，不能验证 G²CP 完整机制的收益。当前 MedQA 路径也不能称为论文 G²CP 的复现。此前将仓库 Control/Semantic/Precise 三层封装直接视作论文协议，是不准确的对应关系。

核查对象是 Karim Ben Khaled、Davy Monticolo 的 [G²CP: A Graph-Grounded Communication Protocol for Verifiable and Efficient Multi-Agent Reasoning，arXiv:2602.13370v1](https://arxiv.org/html/2602.13370v1)。论文的核心是共同知识图谱上的遍历和更新操作，Agent 引用同一批节点与关系，返回子图或路径；它另设自然语言与 JSON 结构化基线。参见第 3 节与第 5.1.4 节。

论文第 6.2.1 节统计 Agent 间消息的文本 Token，以 cl100k_base 计算，排除 Agent 内部推理、用户原问题和最终回答。因此论文报告的通信 Token 降幅不能直接对照本项目的 DeepSeek API 全部 prompt/completion usage。论文第 4.5 节也说明仍使用 LLM 动态选择操作，不能据第 4.3 节的简述声称整个执行链仅有用户边界两次模型调用。

## 源码发现

1. `LangChain/medqa/runtime.py:93` 仅按 mode 切换 `compact(payload)` 与 `render_text(payload)`。二者使用相同业务对象，角色提示不因 mode 改变。
2. `render_text()` 递归保留字典字段、列表与值，文本基线本来就有显式结构，非自由长文本对话。`LangChain/medqa/model.py` 对两种模式均要求 JSON 输出。
3. `Runtime.run()` 在两种模式下都调用 `g2cp_profile.message()`，将控制、语义引用与角色内容分开；只有 precise 进入模型。已有上下文裁剪、来源引用和程序工具执行也是两组共同机制。
4. `LangChain/medqa/g2cp_profile.py` 的 semantic 主要保存 memory_ids 等引用，并未将任务编码成论文定义的图遍历/更新请求。当前语料接口是 Textbooks BM25+MedCPT 搜索和来源回读；未见该路径的共享实体/关系 schema、实体链接与图操作执行器。
5. `g2cp.py` 的类名、字段划分及文件名只能证明本地封装，不能证明引用来源、论文实现一致性或预期性能。程序外控制信息不消耗聊天 Token，但仍消耗存储、通信和计算。

| 当前条件 | 三层封装 | 角色上下文选择 | 模型输入 | 模型输出 |
| --- | --- | --- | --- | --- |
| text | 开启 | 开启 | 同字段可读文本 | JSON |
| structured | 开启 | 开启 | 同字段紧凑 JSON | JSON |

因此，现有小幅差异不构成“论文协议效果差”的证据。它揭示当前分组并未切换最希望验证的机制。数字操作码方案可以独立实现统一协议，但若只在模型生成 JSON 之后转成数字，仍不能将其称为图语义通信或自动宣称降低模型 Token。

## 对实验的修正建议

- 原结果保留，准确命名为“同字段输入表示对照 + 跨题记忆开关”；不删除失败或负收益。
- JSON 是否包含文字不能决定是否结构化。关键是字段和参数是否有确定类型、可执行含义、可核验引用；JSON 也可以承载严格操作协议。
- 后续先固定题目、知识源、工具、记忆条件与质量标准，分别比较自然语言交接、普通字段式 JSON 交接、已实现的操作/引用协议；不为扩大差距人为添加重复历史。
- 新协议单独统计 Agent 消息字节和文本 Token（注明 tokenizer），同时保留全量真实 API usage、状态与登记/解析成本、检索/模型调用和质量。二进制字节不能直接当作模型 Token。
- 若实现的是 ACP-1，报告名称就是自有操作/引用协议；只有实际接入共同知识图谱、实体链接及图操作执行/验证，才讨论对论文 G²CP 的复现或适配。
- 不能为了复现论文指标，预先把 MedQA 标准答案写入图或引用表。构建成本与来源校验应单列；当前题目从教材段落取证，并不天然等同图查询任务。

## 握手与能力发现核查

论文第 3.1、3.4、3.6 节定义发送/接收者、会话标识、请求/通知/确认/拒绝等通信动作和图操作语义；第 4.4 节描述解析、授权、执行与错误处理。在核对的这些流程中，未明确规定 HELLO/HELLO_ACK、能力注册发现接口或协议版本协商。CONFIRM 表示确认操作结果，不能直接等同连接握手。不能仅凭协议名称宣称已经获得课程赛题要求的全部运行时机制。[原文](https://arxiv.org/html/2602.13370v1)

本项目 `Runtime.handshake()` 当前主要生成描述对象，由 CLI 导出 JSON；记忆与检索 worker 另有实际 ready 检查。这些不等于完整的 Agent 能力协商。建议 ACP-1 在运行时实现：HELLO 选择支持版本，注册能力及参数/结果 schema，只有已注册且允许的动作才能派发；未协商、版本不支持、能力缺失、参数/引用无效时返回明确错误。赛题原文为握手、能力发现或协议映射三者之一，并非要求复刻 TCP 三次握手。

## 在现有三 Agent 项目上的最小调整

1. 保留原数据、工具、角色、预算和结果，旧模式准确称为字段文本/紧凑 JSON 格式对照。
2. 为 Agent 间交接明确两个实现：TextHandoff 将当前交接所需任务、请求和发现表达为可读文字；ACPHandoff 将动作和结果编码成受校验的消息、类型参数与引用。工具内部仍可使用同一 Python/JSON 接口，不能按系统里是否出现 JSON 判定通信模式。
3. 两组保持相同知识访问权限与质量要求，不给文本基线人为填充历史；握手/能力信息属于模型外机制，不应伪装为省去模型 Token 的主要来源。
4. ACP 的对象存储应真实保存内容，接收方按需解析；模型视图与生成输出的精简另做消融，不能只把现有 payload 换成二进制后宣称 API 成本下降。
5. 用原有保存响应先做无损编解码与路由检查，再小样本检验两个交接路径。检查通过后，在新版本目录运行原三组 30 题的四条件对照；此文档没有启动实验。
6. 分别报告 Agent 间消息量、字节与注明 tokenizer 的文本长度，全量真实 API 输入/输出、对象登记和补取成本、状态消费、准确率与运行失败。二进制字节与 API Token 分栏呈现。
