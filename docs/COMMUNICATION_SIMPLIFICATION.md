# 数字协议解析与全流程信息精简

这是协议设计过程中的精简建议。独立数字协议示例已由正式ACP-1实现替代并清理；当前代码与验证边界见[实现说明](COMMUNICATION_IMPLEMENTATION.md)，本提案不代表全部已经实现。

解析器使用版本化协议表解释数字，不调用 LLM。字段的位置、数据类型和操作码共同确定含义；同一个数在来源、动作、参数中的含义由字段决定。任意新问题、查询和医学判断不能凭空编号：必须保留原文，或先登记到接收方可访问的对象存储。引用按任务作用域解析，映射到不可变内容及内容哈希；跨任务复用应由持久化记忆 ID 或内容哈希映射，不能复用碰巧相同的局部编号。

示例头部使用网络字节序，字段为版本 u8、类型 u8、源 u8、目标 u8、操作码 u16、任务 ID u32、请求 ID u32、消息体长度 u32，共 18 字节。消息体按操作码解码；数字打印形式只是调试视图，实际传输 bytes。

| 操作码 | 动作 | 参数布局 |
| --- | --- | --- |
| 10 | 教材搜索 | query_ref:u32、top_k:u32 |
| 20 | 读取记忆 | memory_ref:u32 |
| 30 | 证据区间引用 | evidence_ref:u32、start:u32、end:u32 |
| 40 | 提交选择题答案 | option:u8、evidence_ref:u32、support:u8 |

30 的区间是 Python 字符串的 Unicode 字符下标，左闭右开；不是 UTF-8 字节偏移。40 只是单来源、四选一的简化示例；真实系统仍需多来源列表、来源有效性核验和必要的判断文本，不能将支持状态码视为支持事实的证明。该示例检查编码和基本数值范围，不执行权限、路由、重复请求或业务证据校验；正式接入仍需这些检查。

例如头部 `1,1,2,4,10,17,42,8` 与参数 `1001,3` 表示：版本 1，请求消息，检索 Agent → 教材工具，任务 17 的请求 42，执行搜索，查询引用 1001，最多返回 3 条。接收方先在任务 17 的对象表解析查询 1001，然后调用工具。若引用不存在，返回明确错误；不得自行猜测或使用旧任务的同号对象。

## 全流程精简清单

| 传递步骤 | 信息 | 可以怎样精简 | 必须保留的内容及边界 |
| --- | --- | --- | --- |
| 启动与握手 | 角色名、能力表、协议版本、模型/向量版本 | 连接建立时协商字典和版本；后续用 Agent ID、能力位图、版本 ID | 遇到未协商版本或操作码明确报错；当前能力控制层本就不进入模型 |
| 调度 → 各 Agent | trace、任务主题、时间、路由、动作 | 使用数字头部；日志保存长 trace 和时间，模型输入省去可由程序提供的字段 | 请求与任务关联、错误归属、幂等与审计不能丢失 |
| 任务初始化 → 各阶段 | 原题与选项 | 对象存储保存一次，进程间传 task_ref；模型适配层按角色构建必要视图 | 独立云 API 调用不会自动知道上一角色上下文；验证角色保留原题与全部选项，不能只信规划摘要 |
| Planner → Investigator | 条件、知识需求、关联、固定验收模板 | 规划产物存一次；后续传 plan_ref、需求 ID、条件位图；省去固定验收模板、空依赖和重复解释 | 保留待核实需求、否定、人群、时间、数字和单位；自定义事实不能用无字典数字代替 |
| Investigator → 工具 | 查询、条件执行策略、数量、预算 | 操作码＋query_ref＋top_k；run_if 用枚举；依赖用查询 ID；程序执行预算与去重 | 首次查询文本必须存在；备用查询触发语义不能改变 |
| 工具 → 验证角色 | 文档正文、标题、哈希、重复命中、分数 | 正文按哈希缓存；返回 doc_ref 和区间；按需求取最小充分原文、去重；不向模型投递无用排名元数据 | 验证所需原文、反证、否定、例外和来源绑定；已有证据处理器也已做部分筛选，不能把建议全部视为当前缺失 |
| 记忆 → Planner/Investigator | 记忆摘要、来源条件、旧查询和执行经过 | 先给短预览，确认采用后解析；事实/策略/过程用类型码，只传当前角色所需部分 | 当前已有最多 3 条预览及按角色裁剪；旧病例条件不等于通用适用规则，策略不等于医学证据 |
| 状态交换 | embedding、维度、类型、模型版本 | 继续 float32 原始字节传输；大对象可探索共享内存引用；减少无变化状态重复发送 | 接收方实际使用向量且校验模型/维度；数字引用不能单独充当非文本语义状态的效果证明 |
| 首次处理 → 补查 | 已知证据、任务状态、缺口、冲突 | 接收程序保留状态版本，仅发新增/变更/删除及基线版本；缺失基线时恢复快照 | 云模型请求仍需必要上下文；补查只给增量且完全省掉原条件可能造成错误 |
| 验证角色 → 调度/报告 | 答案、证据状态、引句、解释、重复题号 | 答案/状态用枚举，引用用 source_ref＋span；程序补任务 ID、时间、来源元数据；保留必要短解释 | 模型需选择正确区间，程序核对原文；不要仅为压缩强迫模型数长文本字符，可用预编号的候选原文区间 |
| 执行 → 共享记忆 | ID、来源 Agent、时间、主题、摘要、证据、经验 | 程序生成元数据；正文复用内容引用；相同内容去重，按变化更新索引 | 赛题要求的元数据仍完整保存；不是为了减少消息字段而从记忆中删掉 |
| 全流程日志与统计 | 全量控制信息、重复原文、计费、状态传递规模 | 原文存一次、日志按引用关联；通信只传必要字段，审计可回溯 | 同时报字节、模型输入/输出 Token、编码解析耗时、字典/对象登记成本、准确率与总耗时 |

## 优先级与统计边界

优先处理证据投递、模型输出冗余和角色所需状态，其次做引用与增量同步，最后优化本来就在模型外的控制头。当前程序已省略部分执行历史，已有 float32 记忆 IPC；这两点应保留并测量，不能作为待实现功能重复宣传。

此前对四条件共有 28 道已回答题的诊断中，结构化有记忆条件 evidence_pool 字段值累计 151,947 字符，题干 59,274、选项 11,430、规划条件/需求/状态 43,954、记忆信息 26,217、预算 14,364；系统提示另计 87,360。它们是对应字段值序列化后的字符统计，不能直接折算 Token 或全部算成可删除冗余。原始统计见该批次 `protocol-audit.json`。

二进制编码减少的是消息字节。引用减少重复搬运，但如果模型适配层仍展开所有正文，API Token 仍会重复产生。真正减少模型 Token 需要角色视图和必要证据选择，并验证不会损失正确率。云 API 的 JSON 响应外壳可以继续用于提取模型意图；由程序转成二进制 Agent 消息，不需要模型自行生成二进制包。

同一逻辑消息应分别以现有 JSON 和数字二进制编码，先做无 API 的无损回放比较；正文、字典登记与缺失引用补取都纳入成本。再单独比较完整上下文与按角色/缺口裁剪后的模型输入，保持题目、工具、模型、质量标准一致。不要把格式编码与内容压缩混成一个无法解释的收益数字。
